# Формат данных для муниципальной сверки

Одна рабочая база относится к одному согласованному контуру дел и начислений. Сначала загрузите реестр дел, затем опись актов и выписки. Обмен выполняется локально в разделе «Импорт из ИС». Готовые учебные образцы лежат в `examples/municipal/`. Файл платежей и опись актов загружайте на своих вкладках. Папка incoming принимает только дела.

## Общие правила

Принимаются CSV и первый лист XLSX, до 5000 строк в каждом файле. Для генератора используйте CSV в UTF-8 с заголовком и разделителем «точка с запятой». Технические имена ниже указаны точно. Даты передавайте в формате ГГГГ-ММ-ДД, суммы в рублях, пустую ячейку используйте для неизвестного значения. Число 0 означает установленный ноль. Все идентификаторы в Excel храните текстом, чтобы сохранить начальные нули. Связь строится по точному идентификатору, с учётом регистра и после удаления пробелов по краям.

## Реестр дел

Одна строка соответствует одному делу. Для совместимости оставьте все прежние заголовки, даже если часть ячеек пустая.

```text
case_id;case_type;application_date;issued_date;predecision_date;documents;documents_complete;accrued_amount;paid_amount;exemption_code;exemption_proof;comment
```

Номер дела case_id должен быть уникален. В учебном профиле case_type принимает standard или emergency. Даты обозначают заявление, выдачу билета и предварительное решение соответственно. В documents запишите названия через вертикальную черту, например «Заявление|Акт обследования». documents_complete принимает yes или unknown. accrued_amount и paid_amount задают начисление и оплату по карточке. exemption_code содержит код заявленного освобождения, exemption_proof принимает yes, no или unknown. comment содержит пояснение. Сохраняются прежние необязательные finance_mode и payment_note.

Дополнительные колонки для местной работы:

| Поле | Значение |
| --- | --- |
| permit_stage | pre_issue до выдачи, issued после выдачи, unknown при неизвестном этапе. Заполненная issued_date определяет этап «После выдачи». Старое дело без даты и этапа требует уточнения. |
| charge_id | Текстовый номер одного начисления по делу. Один и тот же идентификатор используют реестр и бухгалтерия. |
| permit_act_number, permit_site, permit_trees | Ссылка на акт, код участка и количество деревьев из проекта или выданного билета. |
| act_number, act_site, act_trees | Те же реквизиты из подписанного акта. Их можно получить отдельным файлом. |

Количество деревьев является целым неотрицательным числом до семи цифр. Для участков согласуйте один справочник, для количества один вид работ и одну единицу измерения. Случаи с несколькими актами, начислениями или участками требуют отдельного разбора. Пустые дополнительные колонки при повторном файловом импорте сохраняют прежние сведения. Для очистки реквизита используйте редактирование карточки. Остальные поля дела действуют по прежним правилам импорта.

## Опись актов

```text
case_id;act_number;act_site;act_trees
МУН-001;А-18;УЧ-07;8
```

Все четыре значения обязательны. Дело должно быть в реестре. На одно дело передайте одну строку. Сначала специалист видит предварительный список, затем подтверждает внесение реквизитов. Ошибка останавливает весь файл. Изменение создаёт редакцию с именем исходного файла в истории. При повторной загрузке тех же значений новая редакция не создаётся. Подтверждение полноты описи в R2 выполняется отдельно.

## Выписка бухгалтерии

```text
as_of;case_id;charge_id;paid_total
2026-11-20;;0000901;1200.00
2026-11-20;МУН-002;0000902;600.00
```

as_of задаёт единую дату полного среза по согласованному контуру. paid_total указывает накопительный итог зачислений с учётом корректировок, до двух знаков после запятой. Допустим неотрицательный итог. Бухгалтерия заранее суммирует частичные оплаты по одному начислению. Сырые банковские проводки, отдельные возвраты и дневные обороты требуют подготовки у источника. Для второго среза укажите более позднюю дату и повторите все актуальные строки с полными итогами. Повтор того же среза безопасен. В журнале хранится один сохранённый срез на дату.

Нужна хотя бы одна колонка связи, case_id или charge_id. Если номера начислений есть в обоих источниках, они должны совпасть. Иначе сервис использует точный общий номер дела. Если оба номера указывают на разные дела, номер повторяется или связь отсутствует, специалист получает задачу на сверку. Пустая сумма и отсутствие строки сохраняют неопределённость. По освобождённому делу неожиданное поступление требует уточнения. Сумма на дату среза сама по себе не устанавливает дату оплаты относительно выдачи.

## Как проверять сгенерированные данные

Передайте четыре файла по образцу из examples/municipal. Для МУН-001 задайте начисление 2500 рублей, в первой выписке 1200, во второй 2500. Ожидайте недоплату 1300 и последующее подтверждение. В акте укажите 8 деревьев, в проекте 12. После переноса оплаты расхождение документов должно сохраниться. Для МУН-002 повторите частичную оплату, для МУН-003 пропустите строку выписки, для освобождённого МУН-004 оставьте оплату пустой. Добавьте одну строку с неизвестным начислением. Для независимой проверки храните ожидаемые результаты отдельно от входных файлов. Демонстрационные дела не содержат персональных данных.

## Что происходит в SQLite

Сервис сам создаёт миграцию 4 в data/green_control.sqlite3. Сведения дела находятся в cases.payload, снимки редакций в case_versions, результаты R1–R3 в analysis_runs. Новые реквизиты необязательны. Таблица payment_batches хранит дату среза, имя файла, время фиксации и контрольную сумму разобранных строк. payment_results хранит результат сопоставления со значениями на момент сверки, номером строки, ссылкой на дело и его редакцию. Строки без связи имеют пустую ссылку на дело. Явный перенос суммы сохраняет редакцию и её номер в результате сверки. Связанные строки удаляются при удалении дела. Генератор готовит файлы обмена. Запись в эти таблицы выполняет приложение, чтобы сохранить транзакции и историю.
