## 0. Суть проекта и рабочий принцип

«Зелёный контроль» — веб-сервис предварительного анализа решений о выдаче порубочных билетов. Он предназначен для сотрудника, проверяющего разрешительные дела на признаки возможного необоснованного предоставления преимуществ заявителям. Сервис принимает сведения двумя способами: **(А)** непосредственное создание/редактирование дела в интерфейсе; **(Б)** загрузка ведомственной обменной выгрузки CSV/XLSX или импорт из папки `incoming`. Применяет три объяснимых модельных индикатора: **R1** — финансовые условия и основания освобождения; **R2** — наличие предусмотренных документов; **R3** — последовательность действий и дат. Выдаёт результат с доказательствами, планом уточнений и возможностью ручного заключения.

**Важное методологическое правило:** сервис НЕ устанавливает факт коррупции или виновность человека. `FLAG` означает несоответствие установленному проверочному условию; `NEED_DATA` — сведений недостаточно; `PASS` — по конкретному правилу отклонение не установлено; `NOT_APPLICABLE` — правило не применяется. Правила в `config/rules_demo.json` **модельные**. Нельзя выдавать их за нормативно утверждённые для реальных разрешительных дел.

## 1. Исходный проект: что прочитать прежде всего

Работать в существующей папке `green-control` версии 1.4 (или более поздней, если она уже изменена пользователем). Сначала изучить фактическую файловую структуру и тесты; при несовпадении документа с кодом приоритет у реального кода и безопасной миграции.

Ожидаемые исходные компоненты (проверены по архиву MVP 1.4):

- `app.py` — Streamlit-интерфейс (создание, редактирование, реестр, импорт, справка).
- `core/models.py` — `normalize_case`, модель полей, загрузка профиля.
- `core/rules.py` — детерминированные `check_r1`, `check_r2`, `check_r3`, `analyze_case`.
- `core/guidance.py` — рекомендации специалисту и лист проверки.
- `core/storage.py` — SQLite, таблицы `cases` (`case_id, payload, source, saved_at`) и `reviews` (`case_id, decision, note, reviewed_at`).
- `core/importer.py` — XLSX/CSV, каталог обмена.
- `config/rules_demo.json` — модельные категории, условия, исключения.
- `tests/` — 33 проходящих автоматических теста исходной версии.
- `requirements.txt`, `.streamlit/config.toml`, Windows-скрипты запуска, инструкции.

**До первого изменения:**

1. Проверить `git status`, создать коммит/контрольную точку исходной версии, если Git настроен.
2. Скопировать `data/green_control.sqlite3` в резервное место, если база существует. **Никогда не перезаписывать и не удалять рабочую базу без разрешения**.
3. Запустить `python -m pytest -q` внутри существующего `.venv` и зафиксировать результат.
4. Прочитать `README.md`, `docs/WORK_HANDOFF.md`, `docs/RUNBOOK.md`.
5. Сформировать короткий план изменений по файлам. Затем **самостоятельно выполнить** итерацию 1, а не ограничиваться советами.

## 2. Общие технологические ограничения

- Сохранять Python + Streamlit + SQLite; Pandas/OpenPyXL для импорта и аналитики; Pytest для тестов. Не внедрять React, FastAPI, PostgreSQL, Docker-оркестрацию и внешние платные сервисы без технической необходимости.
- Все локальные операции — без зависимости от облачного API. Не обращаться к реальным ведомственным системам, не отправлять данные во внешние сервисы.
- Python-модули с правилами должны оставаться отделены от Streamlit (`core/rules.py`). Интерфейс не должен содержать дублирующую бизнес-логику.
- Профиль правил вынести в конфигурацию с полями `profile_id`, `version`, `status`, применимостью по категориям, обоснованием/описанием. Существующий `rules_demo.json` не превращать в «настоящий муниципальный регламент».
- Детерминированность: один `case`, один `profile/version` → одинаковые результаты R1–R3. Сохранить след использованной версии профиля в результатах.
- Любые изменения данных проходят через валидацию и транзакционное сохранение. Нет частично импортированных или частично пересчитанных наборов.
- В интерфейсе русский язык, аккуратные сообщения ошибок. Не показывать пользователю трассировки стека при обычных ошибках ввода.
- Сохранить принятый стиль: строгий официальный интерфейс, пастельные синие тона; светлый фон, тёмно-синий текст, ясные таблицы и кнопки. Не использовать декоративные эмодзи или кричащие цвета. Для статусов — не только цвет, но и текст.

# ИТЕРАЦИЯ 1. ПОЛНОЦЕННОЕ РАБОЧЕЕ МЕСТО СПЕЦИАЛИСТА

## 3. Навигация и экраны

Преобразовать текущие вкладки в логичную навигацию. Предпочтительно Streamlit `st.navigation`/`st.Page` либо проверенное совместимое решение; не менять фреймворк. Разделы:

1. **Обзор** — ключевые показатели + очередь дел для проверки + последние действия.
2. **Реестр дел** — список, поиск, фильтры, сортировка, переход в карточку.
3. **Новое дело** — создание через интерфейс без Excel, помощь при вводе, сохранение черновика.
4. **Анализ и проверка** — карточка сигналов, разъяснения, недостающие сведения, действия и заключение.
5. **Аналитика** — раздел пока может иметь минимальный каркас, закончить во 2-й итерации.
6. **Отчёты** — экспорт реестра и индивидуального заключения.
7. **Методика и настройки** — действующий модельный профиль, версия правил, смысл статусов, ограничения, инструкция.
8. **Импорт из ИС** — вспомогательный путь, не стартовый экран.

**Обзор** должен быть стартовым экраном. Четыре основные метрики: всего дел, дела с `FLAG`, дела с `NEED_DATA`, завершённые человеческим решением. Агрегация строго по делам, не путать число дел и число сигналов. Показывать очередь приоритетных дел; переход в выбранное дело одним действием.

## 4. Реестр и поиск

- Таблица: идентификатор, категория, дата, источник, версия правил, число сигналов, число `NEED_DATA`, рабочий статус, последнее изменение.
- Поиск по `case_id` и, при наличии, комментарию; фильтры по категориям, периоду, статусу работы, R1/R2/R3, наличию сигнала/нехватки данных, источнику.
- Сортировки и пагинация/управление объёмом для 200–300 записей.
- Открытие карточки без потери текущего фильтра, если позволяет механизм состояния Streamlit.
- Экспорт текущей отфильтрованной выборки в CSV/XLSX; метрики не должны учитывать «скрытые» дела как будто они удалены, если подписи подразумевают весь набор.
- При пустой базе — понятный экран с кнопкой «Создать дело», а не техническая ошибка.

## 5. Создание и редактирование дела

Существующий ручной ввод становится основным сценарием. Сделать понятные шаги:

**Шаг 1. Общие сведения:** `case_id` (автогенерация уникального номера с возможностью ручного ввода), категория дела, даты заявления и выдачи, комментарий.

**Шаг 2. Документы:** необходимые по модельному профилю документы — человекочитаемые названия, чекбоксы. Обязательно различать «документ отсутствует в подтверждённо полном деле» и «состав материалов неизвестен»; нельзя автоматически устанавливать `documents_complete=yes`.

**Шаг 3. Финансы:** выбор: «сведения ещё не получены», «начисление/оплата», «заявлено освобождение». Для платежа — суммы и пояснение; для освобождения — выбор допустимых профилем оснований, наличие подтверждения `yes/no/unknown`. Изменение сценария должно немедленно обновлять поля и очищать несовместимые значения.

**Шаг 4. Проверка и сохранение:** короткое резюме ввода, подсветка пропусков, сохранение черновика либо «Сохранить и проверить».

- Не терять введённые данные при переходах между шагами (через `st.session_state` + явное сохранение).
- Обязательные поля различать для черновика и завершённого ввода. Черновик не обязан проходить все юридические проверки, но должен иметь ID и категорию либо пометку о неполноте.
- Запретить непреднамеренную перезапись существующего дела при совпадении `case_id`: явный режим редактирования/подтверждение.
- После изменения данных прежнее заключение не считать действующим: пометить «требуется повторная проверка»; **сохранить его в истории**, а не безвозвратно удалять. Существующий `storage.save_case` удаляет старую запись `reviews`; заменить это безопасной версионированной логикой.
- Выводить дружелюбные ошибки валидации, например «Дата предварительного решения не указана — R3 пока не может быть проверено» вместо необоснованного обвинения.

## 6. Рабочие состояния дела (не путать с результатами R1–R3)

Добавить жизненный цикл с четырьмя состояниями:

- `new` — поступило/создано; анализ проведён или ожидается.
- `in_review` — специалист рассматривает выявленные условия.
- `awaiting_info` — запрошены дополнительные сведения.
- `closed` — проверка завершена, заключение зафиксировано.

Переходы явно доступны через интерфейс с обязательными комментариями для `awaiting_info` и `closed`. При редактировании закрытого дела не удалять историю: новая версия дела переводится в состояние повторной проверки либо пользователь подтверждает этот переход. Отображать дату и основание каждого перехода.

**Различение статусов:** `FLAG/NEED_DATA/PASS/NOT_APPLICABLE` — статусы отдельных правил; `new/in_review/awaiting_info/closed` — статусы обработки дела человеком. Не смешивать их ни в БД, ни в визуализации.

## 7. Карточка анализа и рекомендации

Для R1–R3 показывать: название, текущий статус, причину результата, исходные значения (evidence), применённое условие из профиля, ограничения, рекомендуемые дальнейшие действия и возможность сохранить комментарий специалиста. Использовать имеющийся `core/guidance.py`.

- Статус `PASS` не равен «разрешение законно».
- Статус `FLAG` не равен «коррупция установлена».
- `NEED_DATA` никогда не учитывается как доказанное нарушение.
- `NOT_APPLICABLE` не участвует в метрике доли успешно пройденных применимых проверок.
- Результат должен содержать ссылку/идентификатор применённого профиля и его версию.
- Превратить рекомендации из пассивного текста в действия: «Запросить сведения», «Отметить рассмотренным», «Отклонение подтверждено документально», «Сигнал снят», с датой, комментарием и фиксацией в истории.
- Запрос документа — пока локальная запись задачи, не реальная отправка служебного запроса во внешние системы.

## 8. База данных, история и совместимость

**Текущая структура:** `cases(case_id, payload, source, saved_at)` и `reviews(case_id, decision, note, reviewed_at)`.

Сделать миграции SQLite, не уничтожая данные. Минимум:

- `schema_migrations` — версия схемы и дата применения.
- Сохранять актуальную карточку и её ревизию (`version`) — можно расширить `cases`, но старые строки должны остаться читаемыми.
- `case_history` или `case_versions` — снимок содержимого до/после редактирования, время, тип события, условный инициатор «Локальный оператор» (не выдавать за реальную персональную авторизацию).
- `case_workflow_events` — переходы состояний, заметки, даты.
- `review_history` — предыдущее и текущее заключения; старые заключения не удалять бесследно.
- `analysis_results` или `analysis_runs` — версии и результаты R1–R3 для соответствующей ревизии дела, версия профиля, время расчёта; старый результат помечать историческим после изменения входных полей.

Если временно проще реализовать часть истории в JSON, допустимо, но должна быть **устойчивая, доступная в интерфейсе и экспортируемая история**, а не только session_state.

Обеспечить транзакционность: импорт пачки либо полностью проходит, либо откатывается. Включить безопасную обработку дублирующего `case_id`, ограничения длины комментариев и защиту от некорректных значений/пустых полей. Применять параметризованные запросы SQLite.

## 9. Ограниченная модель безопасности MVP

- Работать локально, предпочтительно привязка к `127.0.0.1`. Без публикации в Streamlit Community Cloud и без передачи реальных персональных/служебных сведений.
- Не создавать фальшивую авторизацию (например, логин admin/admin без защиты) и не заявлять, что есть полноценная ролевая модель.
- Реальная многопользовательская идентификация и журнал аудита с подтверждённым пользователем — отдельный этап промышленного внедрения.
- Для демонстрации использовать синтетические данные, технические ID и обезличенные значения.
- В интерфейсе оставить в «Методике и ограничениях» честную оговорку о модельном профиле и решении человека. Можно убрать раздражающие плашки со стартового экрана, но не скрывать эту существенную информацию.
- Отдельно задокументировать ограничение SQLite при одновременной работе многих сотрудников и будущую миграцию на PostgreSQL.

## 11. Приёмка итерации 1 — обязательные тесты

1. Все исходные 33 теста продолжают проходить либо корректно обновлены при документированном изменении поведения.
2. Создание дела вручную → сохранение → открытие в реестре → R1–R3 → заключение → история — проходит целиком.
3. Черновик сохраняет частично введённые сведения; после повторного открытия продолжает редактироваться.
4. Изменение карточки не уничтожает старое заключение и результат: они доступны как исторические, актуальный анализ пересчитывается.
5. `NEED_DATA` не становится `FLAG` из-за пустых полей.
6. Старые сохранённые дела в исходной БД читаются после миграции, их данные не теряются.
7. Повторный запуск миграции не ломает БД.
8. Условные финансовые поля работают корректно после переключений.
9. Нет ошибок Streamlit `DuplicateWidgetID`, потери состояния формы или повторного импорта при простом обновлении.
10. Успешная проверка в браузере `http://127.0.0.1:8501` хотя бы двух сценариев: корректное дело и дело с отклонением.

**По завершении:** оставить приложение работающим, выдать перечень изменённых файлов, результат тестов, 5–8 скриншотов или чёткие указания, где посмотреть изменения, и список замечаний. Перед итерацией 2 сделать Git-коммит/точку восстановления.

# ИТЕРАЦИЯ 2. АНАЛИТИКА, ДАННЫЕ, ОТЧЁТЫ И ПОДГОТОВКА К ЗАЩИТЕ

## 12. Синтетическая тестовая база

**Только после стабилизации итерации 1.** Создать воспроизводимый генератор `scripts/generate_synthetic.py` с фиксируемым seed и командой запуска. По умолчанию — около **200 синтетических разрешительных дел**; число настраивается параметром. Сценарии:

- корректные платные разрешения;
- подтверждённые разрешённые освобождения;
- R1: неполная оплата или отсутствие доказательства основания, с отдельным случаем `NEED_DATA`;
- R2: отсутствие обязательного документа при подтверждённо полном деле;
- R2: неизвестная комплектность (`NEED_DATA`), даже если часть документов не указана;
- R3: дата выдачи раньше обязательного предварительного решения;
- R3: неприменимый сценарий (согласно модельному профилю);
- смешанные R1+R2, R2+R3, R1+R3;
- пограничные значения: пустые суммы, одинаковые даты, переплата, повторный ID (как негативный тест импорта), корректные законные исключения.

Выходные файлы:

- `data/synthetic/dataset.csv` / `dataset.xlsx` (при необходимости несколько листов, но один файл должен импортироваться существующим импортёром);
- `data/synthetic/ground_truth.csv` — **заранее определённый эталонный статус R1–R3 по каждому делу**;
- `data/synthetic/generation_manifest.json` — seed, версия генератора, дата, число и распределение сценариев;
- `data/synthetic/README_DATA.md` — словарь данных, правила генерации, источник (полностью синтетический), ограничения, импорт, восстановление;
- по возможности отдельная готовая SQLite-база **только для демонстрации**, не заменяющая существующую рабочую `data/green_control.sqlite3`.

**Ключевое методологическое требование:** `ground_truth.csv` формируется по заранее заданным сценариям генератора, а не путём копирования `analyze_case`. Это предотвращает круговую «валидацию самой системы по самой себе». Набор должен включать реально сложные для правил `NEED_DATA`/`NOT_APPLICABLE` и случаи законного исключения. Не называйте тестовую разметку доказанными реальными коррупционными случаями.

## 13. Интерактивная аналитика

Сделать «Аналитика» с контролируемыми фильтрами: категория, диапазон дат, состояние дела, наличие `FLAG`, `NEED_DATA`, конкретный индикатор, источник данных. Показатели на уровне выбранной совокупности с ясным знаменателем:

- количество дел;
- количество дел хотя бы с одним `FLAG`;
- количество дел хотя бы с одним `NEED_DATA`;
- количество дел со статусом `closed`;
- число срабатываний отдельно R1/R2/R3;
- распределение по времени (только если даты корректно определены);
- очередь дел с сигналами и кликабельный переход к карточке.

Диаграммы — строго информативные (столбцы, линии), с подписями и понятными единицами. Никаких вымышленных «бюджетных потерь» или «предотвращённых коррупционных преступлений». Модельный показатель экономического риска можно показывать только как сумму проверяемых расхождений и с явным предупреждением, что это НЕ установленный ущерб.

## 14. Измерение качества

Добавить `scripts/evaluate_synthetic.py` и формирование отчёта `evaluation.md`/`evaluation.json`:

- Таблица ошибок по каждому R1/R2/R3 на тех сценариях, где назначена проверяемая эталонная метка; TP, FP, FN, TN, precision, recall. Если знаменатель = 0, писать «не определено», а не 100%.
- Учитывать `NEED_DATA` и `NOT_APPLICABLE` отдельно; не относить их автоматически к TP/TN.
- Coverage — доля применимых проверок, в которых удалось вынести `FLAG` или `PASS`, отдельно от точности.
- Время анализа 1, 100, 200 дел — измеренное в конкретной среде и с описанием машины, без обещаний производительности ведомственного сервера.
- Детерминированность: запуск 2 раза с теми же данными/профилем даёт идентичный структурированный результат.
- Честно написать, что тесты на синтетике показывают воспроизводимость правил для заданных сценариев, но не доказывают способность выявлять реальные коррупционные действия.

## 15. Отчёты и экспорт

Минимум:

1. **Индивидуальный отчёт по делу:** ID, категория, входные данные, дата/версия анализа, профиль и его статус, R1–R3 (статус, доказательства, объяснение), план действий, заключение специалиста, история.
2. **Сводный отчёт по выбранному периоду:** число дел, статусы, распределение правил, приоритетный список проверок, дата и параметры фильтров, ограничения методики.
3. **Экспорт:** CSV/XLSX гарантированно; PDF желательно, если не требует рискованных дополнительных зависимостей и не ломает запуск на Windows. Допустим надёжный HTML для печати в PDF, если это улучшает надёжность.
4. **Результаты испытаний:** отдельный отчёт без ручного переноса цифр.

Структура отчётов должна быть воспроизводимой, не включать имитации официальных подписей, печатей или утверждения реальными должностными лицами.

## 16. Удобный режим демонстрации

- В интерфейсе предложить **«Загрузить тестовые дела»** с предупреждением и подтверждением; данные полностью синтетические. Это не должно перезаписывать уже существующие записи незаметно.
- Возможность выбрать 3 заранее описанных контрольных сценария: корректный, `FLAG`, `NEED_DATA`.
- Кнопка «Перезапустить анализ» для выбранного дела и, если безопасно, для всей выборки.
- Экран «Методика и ограничения»: какие правила применяются, почему нельзя трактовать результат как доказательство коррупции, какие данные необходимы для внедрения.
- В README дать сценарий видеодемонстрации: создание → проверка → запрос информации → заключение → аналитика → отчёт.
